# 稳定化与模块重构验收

## 业务规则

- 工作更新和项目报告是两种记录：更新描述事项进度；日报/周报是用户主动提交的总结，不自动互相生成。
- 事项增加可空 `project_id`，原始 `project` 文本始终保留。迁移只关联名称精确且唯一的项目，其他记录由事项编辑页人工选择项目。
- 工作更新仍是同一组织内的透明协作数据；分组不是独立租户。不能把本实例当成多个互不信任组织的数据隔离系统。
- 管理员管理全部事项。项目关联事项由当前负责人或该项目所属组的实际组长管理，且必须仍有项目访问权；没有项目关联的旧事项由负责人或管理员管理。单独的 `leader` 标签不授予跨组事项管理权。
- 项目管理权来自 `groups.leader_user_id`；`users.role` 决定界面角色和管理员权限。移除最后一个组长任命会降为组员；手动降为组员会清除所有组长任命。
- 报告：管理员可查看全部；私密报告只供作者和管理员查看；同组报告仅本组可见；公开报告供所有已登录用户查看。项目报告数量和最近报告日期不包含不可见的私密报告。
- 离组作者保留自己报告的读取权，失去修改和删除权。归档项目的报告和关联事项只读；管理员或该组组长可以恢复项目。
- 日报展板按 `update_date <= 所选日期` 的最新更新重建状态、进度和历史负责人。当前标题/项目文本仍显示最新元数据，不是不可变的历史快照。归档不抹去已有工作更新和汇总历史。
- 编辑项目、报告、事项元数据、更新记录的 HTTP PATCH 必须携带 GET 返回的 `version`。缺失返回 428，过期返回 409；界面保留未保存输入供人工合并，重新打开后可读取新版本。删除、归档操作仍使用显式确认。

## 模块边界

| 模块 | 职责 |
|---|---|
| `src/config.js` | 应用、数据目录、备份目录和时区配置 |
| `src/lib/migrations.js` | 编号、事务化、仅执行一次的数据库迁移 |
| `src/db.js` | SQLite 连接、身份/分组、审计、初始化和服务组装 |
| `src/services/projects.js` | 项目与报告访问规则、查询、状态变更和版本保护 |
| `src/services/items.js` | 事项、历史更新、历史视图和汇总 |
| `src/services/exports.js` | Markdown / Excel 格式化 |
| `src/routes/` | 事项、项目报告及运维接口 |
| `src/lib/validation.js` | HTTP 参数约束及分页 |
| `src/lib/observability.js` | 请求标识、结构化日志、错误和限流计数 |
| `public/js/projects.js`、`items.js`、`administration.js`、`groups.js` | 前端业务界面 |
| `public/js/workflow.js` | 草稿恢复、地址导航、未保存保护和键盘焦点 |

前端保持无构建流程，分模块脚本共享 `app.js` 的 API、状态和渲染工具。拆分是渐进式的；未引入微服务、ORM 或新的前端框架。

## 数据完整性与保护

- 分组批量操作、组长任命、记录修改/删除和事项重算使用可嵌套事务。
- 审计记录保留报告/事项/更新记录修改前后值、用户及分组管理操作；密码哈希、密钥和会话版本不写入审计。审计只允许管理员分页读取，不是防数据库管理员篡改的外部审计系统。
- 草稿保存在服务器，按用户和草稿键隔离，最多 100 份，保留 30 天。退出后其他账号无法读取；不使用浏览器持久存储保存私密报告。网络错误时显示保存失败，并保留未保存提醒。
- 事项和项目报告列表默认每页 50 条，最多 100 条。导出最多 10,000 条更新/报告，同时最多两个导出请求；超出要求缩小范围或稍后重试。
- 请求切换日期、事项过滤和项目报告时，旧响应不会覆盖新状态。项目地址支持 `#project/<id>/weekly`；栏目支持 `#view/items` 等地址。

## 验证与界限

执行 `npm run check`、`npm test`、`npm run test:e2e`、`npm audit --omit=dev`。

浏览器首次运行前：`npx playwright install chromium`。也可通过 `E2E_BROWSER_CHANNEL=chrome` 使用已安装 Chrome。端到端测试建立隔离数据库，覆盖首次改密、创建组和项目、周报草稿恢复、保存与编辑冲突、导出、归档恢复、审计查看、地址恢复及手机宽度。

业务测试覆盖事务回滚、周起始日期、归档只读、权限隔离、乐观锁、历史状态、审计、分页、草稿、旧库升级、备份校验和恢复。SMTP 测试通过本机 TCP 接收器执行真实 SMTP 协议，不向外部邮箱发信。

GitHub Actions 已配置语法、测试、浏览器和生产依赖审计；只有推送后才会在 GitHub 执行，仓库中的配置不表示远程运行已通过。

## 性能基线

`npm run benchmark` 在系统临时目录创建 5,000 个事项及 5,000 条更新，输出分页、日报、汇总的 P50/P95、完整 Excel 生成时间与进程 RSS。可设置 `BENCH_ITEMS` 改变规模。

本机测量（Node v24.19.0，5,000 个事项/更新）：事项 50 条分页 P95 11.25 ms，带管理员权限的日报 P95 46.36 ms，汇总 P95 27.69 ms，Excel 生成约 1.46 秒，生成后进程 RSS 349.2 MB。测量发现日报权限逐行查询曾达到约 356 ms，已把管理员所需的归档信息合并进主查询，消除这条路径的逐行查询。

这些数据是单机查询与导出基线，不是并发容量测试或线上 SLA；生产仍是单进程、SQLite，扩容需要另行测量。

## 上线验收边界

代码、测试、迁移和部署模板在仓库内完成。真实域名证书、生产机 systemd 安装、远端备份目标以及企业 SMTP 凭据不在本工作区；操作步骤见 `OPERATIONS.md`。真实团队试运行后的体验反馈和容量调整需要实际运行数据，不能用本地测试替代。
